# Foundry Oracle Ingest Compiler V1 — Final Ratification Candidate

**Date:** 2026-09-20
**Status:** RATIFIED
**Governing principle:** **PRESERVE TRUTH, NOT PLUMBING.**

---

# 1. Purpose

The Oracle Ingest Compiler exists to translate Oracle/card-layout evidence into Foundry's existing mechanical-semantic structures with substantially less human or LLM interpretation.

It is an ingestion and translation frontend.

It is **not** a second canonical semantic architecture.

Its acceptance standard is not "parsed successfully." Its acceptance standard is:

> **mechanically meaningful source material is represented faithfully, scoped correctly, provenance-preserved, and either resolved or explicitly refused.**

A confidently wrong translation is worse than an unresolved translation.

# 3. Three live seams that V1 must not blur

## 3.1 COST

Existing AQ4 benchmark law treats COST as a CR-grounded positional structural region, not a semantic dimension or predicate.

Compiler work MUST NOT reinterpret that region as payability semantics, absence proof, or a new canonical cost ontology.

The important precedent is architectural:

> a useful sub-clause structure may be represented as a deterministic, role-marked region owned by one existing occurrence without adding a fifth occurrence coordinate.

## 3.2 Keyword Consequence Registry

Keyword/rules consequence expansion remains a required ingestion dependency, but its current S16B status must be respected.

Compiler V1 may define the interface it needs from such a registry.

It MUST NOT freeze or populate unratified keyword consequence law by implication.

## 3.3 S16B not frozen

Current S16B concepts are downstream candidate projections, not immutable compiler schema.

The compiler should target lower mechanical truth so later S16B vocabulary changes do not require reparsing Oracle.

# 4. Existing modal/cardinality law is reused, not rebuilt

The earlier V1 proposal incorrectly treated typed choice cardinality as a missing capability.

That is withdrawn.

AQ4 benchmark infrastructure already has generated structural choice groups with:

- owning-header evidence;
- member occurrence addresses using the existing four-coordinate occurrence address;
- selection `{min,max}`;
- deterministic refusal when header residue prevents safe derivation;
- no mode identifier;
- no fifth coordinate;
- no codebook storage;
- no semantic verdict.

Therefore:

> **V1 MUST reuse existing choice/cardinality machinery where it applies.**

Absence of a derived choice group never proves independence.

Compound or otherwise unsupported selection forms remain explicit refusals until separately supported under governing law.

Broader quantity/cardinality needs outside the already-authorized shapes are **extension questions**, not evidence that cardinality is absent.

# 5. V1 priority capabilities

The independent review reduces the main V1 work to four primary capabilities plus three bounded pressure audits.

## M1 — Operation-local structure without premature new identity

The need is real:

one existing clause/paragraph may contain multiple mechanically distinct operations, relationships, or operation-specific qualifiers.

But V1 MUST NOT begin by minting a fifth occurrence coordinate.

### H-REGION

The first hypothesis to test is:

> **H-REGION:** consumer-relevant within-clause operations can be represented as deterministic, source-spanned, role-marked structural regions owned by an existing four-coordinate occurrence, analogous to the already-demonstrated COST-region pattern, without creating a new occurrence coordinate.

This is a hypothesis, not a ruling.

### Required properties

A region candidate must be:

- deterministically derivable;
- source-spanned;
- owned by exactly one existing occurrence;
- contained within the owning face/paragraph/clause;
- stable under repeated execution;
- able to support the relation/qualifier attachment required by the consumer question;
- fail-loud on ambiguity.

### H-REGION kill conditions

H-REGION is killed if a precommitted fixture/population demonstrates that:

- two distinct required operations cannot be given stable distinct ownership inside one occurrence;
- repeated identical operations cannot be distinguished where a consumer requires distinction;
- a relation endpoint cannot be named unambiguously;
- qualifier attachment remains ambiguous;
- overlapping/nested regions create irreducible identity ambiguity;
- a pre-registered consumer question cannot be answered without a stronger identity;
- the representation requires guessed spans or card-specific exceptions.

If H-REGION is killed, the next step is **not** an ad hoc identifier.

The result returns to the existing AQ4 reserved/finer-effect-identity path and Captain governance.

## M2 — Entity / object / set / event reference fidelity

The compiler needs explicit handling of several distinct problems and MUST NOT flatten them into one vague "coreference" system:

1. reference discovery;
2. reference identity;
3. reference resolution;
4. CR object continuity across zone changes;
5. set identity;
6. process/event identity;
7. CR 607 linked-ability relationships;
8. delayed references;
9. complement/partition references.

An unresolved reference is valid output.

A guessed reference is not.

## M3 — Coverage ledger / residue gate

Meaningful Oracle material must not disappear silently.

For each relevant source span or construct, the translation path must account for it as one of:

- existing structural material;
- mechanical fact/occurrence;
- participant/entity/reference;
- predicate/qualifier;
- relation;
- structural region;
- CR/keyword consequence expansion;
- explicitly justified nonsemantic/scaffolding material;
- explicit unresolved/unsupported residue.

This should extend/reuse existing residue, evidence, conservation, and provenance machinery wherever possible rather than create a second accounting system.

Zero visible residue MUST NOT be equated with semantic completeness unless the governing completeness obligations are independently satisfied.

## M4 — Human-readable reconstruction / verbalizer

Reconstruction is validation tooling, not canonical semantic ownership.

Its purpose is:

> let a reviewer inspect what the translator believes the card mechanically says without reading native internal structures.

It need not reproduce Wizards wording byte-for-byte.

It must not become an alternate source of truth.

It may be deferred behind the more fundamental operation/reference/coverage work if required.

# 6. Three Round-2 pressure audits added to V1

The 2026-09-20 Round-2 weird-card evidence identifies three recurring mechanical gaps in the current documented post-audit vocabulary.

These are **audit targets**, not ratified ontology additions.

## R2-A — Generic event replacement / modification lineage

Stress cases include Abundance, Tomorrow, Chains of Mephistopheles, and Uba Mask.

The required truth includes some combination of:

```text
would-be event
→ replacement/modifying effect
→ resulting event or no-event
→ nested resulting event(s)
```

with applicability and CR 614/616 ordering semantics where relevant.

V1 MUST audit whether existing AQ4 relation/event machinery already expresses this faithfully before proposing anything new.

Do NOT create a bespoke `Draw Replacement` family merely to solve event lineage.

## R2-B — Player decision authority

CR 723 player control changes decision authority while not transferring control of the controlled player's objects/resources.

The substrate must be able to distinguish:

```text
A controls B's game decisions during window W
```

from:

```text
A controls B's permanents/cards
```

V1 MUST audit existing participant/authority structures before proposing a new relation/coordinate.

Do not assume this requires a top-level public family.

## R2-C — Ability borrowing / inheritance

Recurring cards gain activated abilities from referenced cards/objects without making those underlying cards playable, cast, copied as spells, or acquired as resources.

V1 MUST audit existing relation/inheritance machinery and measured corpus cases before proposing a new primitive.

Again: a mechanical representation gap does not imply a public ontology family.

# 7. First frontier

The first architecture frontier remains:

> **multiple mechanically meaningful operations and relationships within one existing paragraph/clause surface.**

Reasons:

- reference resolution depends on having stable operation/region endpoints first.

Modal cards remain regression controls rather than the principal proving frontier.

A card may take the deterministic path only when:

- structure closes;
- required references close;

## Tier B — explicit escalation

- unresolved reference;

- nested condition/modality;

# 11. Quality law

The primary failure to minimize is:

> **FALSE SUCCESS**

A visible `UNSUPPORTED` or `UNRESOLVED` result is technical debt.

A plausible but mechanically wrong accepted translation is corrupted truth.

V1 evaluation therefore prioritizes:

1. false-success rate;
2. structural/mechanical fidelity;
3. reference correctness;
4. coverage/residue honesty;
5. historical stability / blast radius;
6. unsupported rate;
7. runtime.

Raw parse percentage is secondary.

# 20. Final proposed Captain architectural ruling

> **The Foundry Oracle Ingest Compiler V1 is ratified as the translation frontend from Oracle/card-layout evidence into existing Foundry mechanical truth. It owns parsing, structural detection, reference-resolution attempts, coverage accounting, and fail-loud translation behavior; it does not own an independent canonical semantic IR. V1 must also audit, without pre-ratifying new ontology, generic replacement-event lineage, player decision authority, and ability borrowing/inheritance. The system minimizes false success, preserves meaningful residue, and fails loudly on unresolved structure or reference.**
