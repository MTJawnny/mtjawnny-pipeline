# PART ONE — PLAIN ENGLISH

**The single most valuable artifact this project has ever produced exists in
exactly one place, on one disk, with no version history, and has never been
restored from backup even once.**

It is `codebook.json`: 403 active axes and 7,930 assertions, **4,233 of them
Captain-ratified by hand** across seven review batches over roughly a month.
Those 4,233 cannot be regenerated by any script. If this workstation's SSD dies
tonight, they are gone, and so are the 31 backups — because the backups live in
the same gitignored directory on the same volume.

**Nobody ever decided this.** The codebook is gitignored by *inheritance*: the
line `experiments/out/` was added to `.gitignore` on 2026-07-07 to keep
tier-engine prototype output out of the repo, and that output was regenerable
scratch. The codebook did not exist yet — its first backup is dated
**2026-07-31, twenty-four days later**. It inherited a rule written for
disposable files.

**And "No card data in git, ever" is a real constraint, not a technicality.**
This repository is **public**. The codebook carries **345,587 characters of
oracle text** in its evidence quotes. Committing it is a redistribution
decision, not a storage decision, and this packet does **not** recommend
overturning that rule.

**The good news is that the project already owns the right machinery and is not
using it for this.** R2 is configured and reachable from this workstation right
now, CI already holds credentials, `pipeline/embed.py` already pulls a
cache file from R2 inside a build, and the bucket already carries a
`data/snapshots/` convention and immutable `data/v/<date>/` paths. The gap is
that the codebook is the one major asset that never joined them.

> **⚠ TWO CAVEATS THE RULING ADDS TO THIS PARAGRAPH.** The credentials CI
> holds are **write-capable**, so they are not evidence of a read-only path
> (P3-5). And the bucket's **privacy is unproven** — it serves the shipped
> site, so public retrievability must be disproven anonymously before any
> Oracle-bearing snapshot is uploaded.

# PART THREE — WHY THE NO-CARD-DATA RULE EXISTS (reconstructed from history)

**Do not assume it should be overturned.** Reconstructed from tracked history
rather than from memory:

- The rule is in the **first commit that created this repo**, `a75ea38`
  (2026-07-03, *"Evening 1: repo skeleton"*), worded exactly as today:
  *"No card data in git, ever. This repo holds code + `tags/` + `recipes/`
  only. `.gitignore` enforces it (`data/`, `*.jsonl`, `*.jsonl.gz`,
  `*.parquet`, `*.sqlite`) — never weaken it."*
- **Every pattern it enumerates is a BULK CORPUS FORMAT.** The rule as written
  is about not committing Scryfall's bulk dumps and their derivatives.
- **`experiments/out/` is NOT in that list.** It was added separately in
  `4eb2f1f` (**2026-07-07**), the tier-engine v1 commit, to keep prototype run
  output out of the repo. That output was regenerable.
- **The codebook did not exist until 2026-07-31** (earliest backup,
  `codebook.v0.7.pre-walk-ratification.20260731-190550.json`) — **24 days after
  the ignore line that now covers it.**
- **No ruling anywhere in `docs/` decides the codebook's durability.**
  `B-MIGRATION-DISCOVERY.md` §5.1 item 6 *states the risk*
  (*"codebook.json has no git history — backup discipline is the entire
  rollback story"*) and §1.2 states the backups are never machine-restored.
  Neither is a decision; both are observations, recorded 2026-08-01 and
  unactioned since.

**The rule's live rationale, as best it can be reconstructed:** repository
size, and — decisively — the repo is **public**, so committing card text is
*redistributing* WotC/Scryfall content under this project's name. The
`docs/OUT-OF-SCOPE.md` precedent that art tags are *"outside evidence law"*
shows the project already reasons about what content it is entitled to carry.

**Finding: the codebook was never the rule's target, but it is squarely inside
the rule's REASON.** 345,587 characters of oracle text in a public repo is card
data being published, whatever the containing file is named. The distinction
that matters is not "is it card data" — it is **"does the durable copy have to
be PUBLIC?"** Every design below is scored on that.

| **A** | **Source of truth** — what artifact is authoritative? | one untracked local file; authority is implicit and unstated |

**Backup ≠ authority, and this is the distinction the packet turns on.** The 31

any other machine, and none is *verifiable* without the prose doc that recorded
its sha. A second copy on the same disk improves neither A, B, C, D nor E.

*Failure mode:* total, silent, and already live. **Its only merit is that it

### C1 — Track `codebook.json` in git
Remove `experiments/out/foundry/codebook.json` from the ignore.

Dur A · Repro **A** · Int A (git hashes) · Roll **A** · Clone **A** · CI **A**

### C5 — R2 versioned snapshots, authoritative *(repository-native)*

> **⚠ SUPERSEDED IN TWO PLACES BY THE RULING.** (1) The mutable `latest.json`
> pointer proposed below is **REJECTED** — a mutable pointer moves authority
> without a commit, which is exactly what P3-1 forbids. Authority is the
> snapshot the **tracked manifest in the current git revision** selects; there
> is no authoritative `latest.json` for the codebook. (2) "private bucket,
> nothing published" was an **assumption, never verified** — R2 privacy is the

`codebook.json` + a manifest written to
`r2:mtjawnny/data/foundry/codebook/<UTC-timestamp>/`, written-once under the
existing immutability flag, with a small mutable `latest.json` pointer written
last — **exactly the ratified `/data/v/<date>/` + `latest.json` discipline

Dur **A** · Repro **A** · Int **A** (sha256 manifest + `corpus_ref` + schema

**private bucket, nothing published, rule untouched** · 2ST **no, if the ruling
names R2 authoritative and local a working copy.**

### C6 — Split model: git holds manifests/hashes only, R2 holds the bytes
C5 **plus** a tracked `docs/codebook-snapshots.json` — for each snapshot: UTC
timestamp, sha256, byte size, axis/member/assertion counts, `corpus_ref`,
schema version, the mutation that produced it, and its R2 path. **No card text
in git; the git history becomes the authenticated INDEX of a durable store.**

Dur **A** · Repro **A** · Int **A+** (git history authenticates the hash; the
hash authenticates the bytes; neither alone is trusted) · Roll **A** · Clone
**A** for *knowing what should exist and verifying what you fetched*, B for the
bytes · CI **A** · Ops B · Cost A · Law **A** · 2ST **no — one authority
(bytes in R2), one index (hashes in git), and the index cannot disagree
silently because it is the verifier.**

*This is `experiments/snapshot.py`'s existing manifest pattern, pointed at the
codebook and at durable storage instead of a gitignored directory.*

### C7 — Reconstructable package
Track the decision files + adapters and rebuild the codebook from scratch.

Dur B · Repro **A in principle** · Int B · Roll C · Clone A · CI C · Ops **F**
· Law **F** — the decision files contain quotes too · 2ST **yes** (the build
and the artifact can diverge).

**Falsified by measurement:** rebuild requires `decisions/*.json` (gitignored,

reconstruction path that has never been executed is a hypothesis, not a
recovery plan** — the same standard that made `EXPECTED_A15_ROWS = 213` a
finding when it would not reproduce.

## 6.2 HISTORICAL — six months from now, recover the codebook for an older migration

- **C0:** only if that machine still exists. The 31 backups are named per
  mutation (`…pre-locality-backfill.20260814-015858.json`), which is genuinely
  good provenance — **and all of it dies with the volume.**
- **C1/C2:** `git checkout <sha>` — excellent, and the repo history would
  correlate codebook state to code state automatically.
- **C5:** fetch by timestamp. Correlating an R2 snapshot to a *repository
  state* depends on the snapshot recording the commit sha.
- **C6:** **strongest.** The tracked manifest is committed alongside the code
  change that caused the mutation, so `git log docs/codebook-snapshots.json`
  answers *"which codebook went with this migration?"* and the sha256
  **authenticates** the fetched bytes. Authenticity is the part C5 alone leaves
  to trust.

**Note the live use case:** `foundry_r5_attribution.py` already replays
`classify_r5` over every codebook backup — an existing consumer of exactly this
capability, currently limited to one machine's disk.

## 6.3 CI — a fresh runner executes all codebook-dependent Gate 2 rows without mutating authority

- **C0:** impossible. 7 rows fail, `family_sweep` masks (§2.5a).
- **C1/C2/C3:** works, at the cost of concern F.
- **C4:** works for ≤90 days, then silently stops having anything to fetch.
- **C5:** `rclone copy` the pinned snapshot read-only. Credentials already
  exist; `embed.py` is the working precedent. **Write-back must be forbidden in
  CI** or an ephemeral runner becomes an author.
- **C6:** same fetch, **plus the runner verifies the sha256 against the tracked
  manifest before running a single gate.** A corrupted or stale fetch fails
  loudly instead of being graded. This is the only design where CI can *prove*
  it graded the intended artifact, which is precisely what stops an ephemeral
  CI artifact from becoming the source of truth.

# PART SEVEN — FALSIFICATION

Attempts to break the preferred design (C6):

1. **"R2 is a single point of failure too."** Partly true — it is one vendor.
   But it is off-machine, off-site, credentialed, and already trusted with the
   ~50 GB image corpus and every shipped artifact. **If R2 is not trustworthy
   enough for the codebook, then the product's entire delivery path is already
   untrustworthy.** Object versioning on the bucket should be *verified*, not
   assumed — it is not confirmed in this packet.
2. **"The manifest is a second source of truth."** The strongest objection.
   Answer: the manifest carries **no content**, only hashes and counts, and it
   is the **verifier** rather than a parallel copy. It cannot silently disagree
   — a disagreement is a halt. It would become a second source of truth only if
   someone edited it by hand, which is the existing G4 generated-artifact rule.
3. **"This is backup theatre until a restore is tested."** **Correct, and
   conceded.** Nothing in §2.4 has ever been restored. Any ruling must carry a
   restore drill or it repeats the failure it is fixing. See Part Nine.
4. **"Snapshot on every mutation will be noisy."** 8 ratified mutations in ~6
   weeks. 5 MB each. Non-issue.
5. **"C1 is simpler and you are avoiding it for ceremony."** No — for
   publication. If Captain rules that oracle-text quotes in a public repo are

# PART NINE — MIGRATION, DRILL AND CI IMPLICATIONS

**Migration.** No codebook mutation. No schema change. No `.gitignore` change
under C5/C6. First snapshot is a copy of the current file at the sha in §2.1,
plus a new tracked manifest. Fully reversible: delete the manifest, stop
pushing.

**Restore drill — REQUIRED.**

> **⚠ SCOPE CORRECTED BY THE RULING.** This section proposed the drill as a
> precondition *of the ruling*. Captain ruled otherwise: **the architecture is
> approved BEFORE the first snapshot exists**, and the drill is a precondition
> to **AUTHORITY CUTOVER / P3 CLOSURE**. Until it succeeds, the **local
> codebook remains the operational source** and any snapshot is a **CANDIDATE**.
> Promotion requires all five: privacy proof · remote readback + hash match ·
> fresh restore · Gate-equivalence · corrupt-byte negative control that HALTS.

The steps:

1. Push snapshot; record sha, counts, `corpus_ref`.
2. **In a scratch directory, not the live tree**, fetch it fresh.
3. Verify sha256 against the tracked manifest.
4. Run the 7 codebook-dependent Gate 2 rows against the restored copy and
   require the same result as the live file.
5. Record the drill and its date. **Re-run it on a schedule** — an untested
   restore is exactly the state §2.4 measures today.

**Negative control:** corrupt one byte of the fetched copy and require the
verification to HALT. A guard never shown to fail is not known to be a guard.

**CI.** Foundry CI is **read-only** (P3-5). Fetch + verify + run the 7 rows,
no write-back.

> **⚠ CORRECTED.** Elsewhere this packet treats "credentials already in
> Secrets" as though it settled CI access. It does not: the existing
> production Actions credentials are **write-capable** (`pipeline/upload.py`
> and `pipeline/embed.py` both write with them), so they are **not** proof
> that a read-only path exists. **Separate read-only Foundry credentials are
> an implementation requirement/preference.** The masking fix this section
> asks for first is **done** — P3-6, 2026-08-14.
